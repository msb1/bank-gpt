# Fictional tenant security demonstration

## Scope and identities

This is a local exercise with three invented institutions and 25 invented customers. It demonstrates that a bank employee can act only within a tenant where they have a role. It is not an identity provider, a production vault, or an integration with bank records.

| Tenant ID | Institution | Member IDs | Users |
| --- | --- | --- | --- |
| 1 | North Harbor Credit Union | `10001`–`10009` | `north_reader` (reader), `shared_reader` (reader), `north_operator` (operator) |
| 2 | Pine Valley Bank | `20001`–`20008` | `pine_reader` (reader), `shared_reader` (reader), `pine_operator` (operator) |
| 3 | Cedar Community Bank | `30001`–`30008` | `cedar_operator` (operator) |

The fixture uses `tenants`, `users`, `user_tenant_roles`, `customers`, and `accounts` SQLite tables with foreign keys. Foreign-key enforcement is enabled on each connection. All member names and balances are fictitious. The SQLite file is ignored by Git and can be regenerated by removing it while the API is stopped.

All passwords below are fictional demo credentials: `north_reader / north-demo-pass`, `pine_reader / pine-demo-pass`, `shared_reader / shared-demo-pass`, `cedar_operator / cedar-demo-pass`, `north_operator / north-operator-pass`, and `pine_operator / pine-operator-pass`.

## Authentication and authorization

`POST /auth/token` accepts the fixture username and password and returns a 15-minute signed bearer JWT. Passwords are stored as salted `scrypt` hashes in SQLite. The JWT identifies the actor (`sub`) and is checked for signature, issuer, audience, and time bounds. Tenant roles are **not** accepted from request bodies or JWT claims. The gateway reads the user's current tenant role from SQLite on each authorization decision. This is a deliberately small local token issuer, not a complete OAuth2 or OpenID Connect provider.

Every discovery request names a tenant. The API checks the actor's `capability:run` permission in that tenant **before** connecting to Playwright. Schema 2.0 saves a tenant-neutral base flow and a separate draft tenant binding. A tenant operator evaluates a draft with a separate grant, submits at least three matching run IDs for a stability report, and may approve it when the success rate is at least 0.9; an operator in another tenant cannot do this. Regular replay requires current membership and an approved binding for the requested tenant. Capability reads and run inspection have the same boundary. Run inspection is additionally limited to the actor who started that run. Operator actions and run closure require an `operator` role in the run's tenant, and audit events record the operator's user ID.

`POST /capabilities/{id}/grants` requires an identity bearer token. After checking current SQLite membership and the approved binding, the gateway issues a two-minute `secure_permissions` JWT for one subject, tenant, base ID, and `replay` operation. An operator may obtain an `evaluate` grant for an existing draft binding. The grant includes its own audience and unique `jti`. Replay requires both `Authorization: Bearer <identity>` and `X-Secure-Permissions: <grant>`, verifies the subjects and scope match, and checks current membership again. Identity, browser-session, and permission tokens have distinct audiences, token types, and required and forbidden claims; one cannot substitute for another. The grant contains no URL or locator and never changes the base contract or action policy. The catalog and FastMCP tool calls use the same tenant role and binding approval checks as HTTP.

A browser run receives a separate signed, short-lived, HttpOnly cookie containing its actor, tenant, and run IDs. The cookie has a different audience from the API bearer token, so it cannot be substituted for the API token. The demo UI checks the cookie and current SQLite membership across its `/demo` routes, including the tenant-specific view, search, result, and verification handlers. Account lookup goes through `TenantGateway.balance`, which scopes its SQL query to the authorized tenant and member ID. A member ID belonging to another tenant returns `Member not found` to avoid revealing that it exists elsewhere.

## Allowed and denied examples

- `north_reader` with tenant 1 can find `10001` and read its savings balance.
- `north_reader` with tenant 1 searching for `20001` receives `Member not found`.
- `north_reader` requesting discovery for tenant 2 receives HTTP 403 before a browser starts.
- `shared_reader` can run the same base capability ID for tenants 1 and 2 when each tenant has an approved binding and a separate scoped grant. The two bindings point to visibly different UIs and account queries remain scoped to the selected tenant.
- `north_reader` cannot take over an intervention. `north_operator` can operate a paused tenant 1 run; `cedar_operator` cannot. The live handoff trace checks HTTP 403 for both forbidden actors on action and resume endpoints.
- Opening `/demo` directly without a run-bound browser cookie returns HTTP 403.

## Why there is no encrypted SQLite vault

The earlier XOR/base64 sample is obfuscation, not encryption, and a hard-coded key would not protect the data. This fixture contains only fictional data, so SQLite stores it plainly and is excluded from Git. The JWT signing key lives in ignored `.env` or the process environment, outside the database and version control. A real secret store would use a maintained authenticated-encryption implementation and separate key management; the assignment does not require one for fake records.

## Limits

The fixture includes documented demo passwords and a local token issuer. Use it only with invented data on a trusted development network. HTTP transport, the unauthenticated remote Playwright server, process-local browser runs and search state, no identity token revocation, and heuristic log redaction remain unsuitable for a real bank. Membership removal takes effect immediately for grant issuance and use. The API checks allowed top-level routes and visible click destinations, and Playwright aborts browser-context requests outside the configured origin and route allowlist. The operator console uses a bearer token but has no visual stream or notification queue.
