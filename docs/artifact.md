# Shared capability artifact, schema 2.0

`artifacts/{id}.json` is a base capability for a vendor product and version. It contains the typed input and output contract, ordered logical steps, condition codes, checkpoint, and allowed actions. Each step names a logical control such as `member_input`, `search_button`, or `balance_cell`. The base contains no tenant ID, route, or locator.

`artifacts/{id}.tenant-{tenant_id}.json` is a tenant binding. It contains the entry URL, origin, UI title and version fingerprints, locator candidates for every logical control, optional reviewed locator overrides, and an approval state. `success_marker` is the checkpoint control. The binding cannot add steps, change parameter or output types, or grant a new action. Runtime policy checks the effective URL, action, risk, and unique visible target independently of the artifact. A binding must cover every base control and its ID must match the base.

Published binding JSON uses `http://192.168.z.zz:8000` for the API machine's origin. `ArtifactStore` substitutes the one allowed origin from ignored `.env` when it loads a binding and substitutes the publication origin again when it writes a new binding version. The configured allowed origin is still checked by the runtime policy. Set `BANKGPT_ARTIFACT_PUBLIC_ORIGIN` in `.env` to the publication placeholder and `BANKGPT_ALLOWED_ORIGINS` to the real, reachable origin. Historical evidence JSON also has masked addresses; it is a record of results, not a source of runtime URLs.

Discovery compiles the observed tenant 1 steps into a base and a **draft** tenant 1 binding. A client submitting another tenant's binding must send a version 1 draft with empty reviewer and stability fields; the API records the submitting operator. An operator can evaluate a draft with an `evaluate` grant, submit at least three run IDs to the stability endpoint, and approve only when the success rate is at least 0.9. The review records the operator, time, supporting run IDs and counts, and base and binding versions. Operators can revoke an approved binding or submit a new draft revision for locator review. Regular replay, the catalog, and invocation require an approved binding. The same base ID is used for both tenants; their selectors and routes differ.

Version `1.1` files remain in `artifacts/` as historical evidence. Reading or replaying one returns HTTP 422 with `unsupported artifact schema 1.1; rediscover as 2.0`. They are never interpreted as version 2.0 or silently migrated. Base IDs are immutable. Each binding state is preserved at `artifacts/{id}.tenant-{tenant_id}.v{version}.json`; the unversioned file is the current pointer. The existing version 1 bindings were snapshotted before this migration. Approval, revocation, and revision create a new immutable version and atomically replace the current pointer.

The generated pytest check in `evidence/codegen/generated_test.py` was produced from base ID and immutable tenant binding version. It reads input values and tokens from environment variables, checks that the current approved binding still has the expected version, invokes HTTP replay, and asserts declared outputs and the final checkpoint. It contains no literal member ID, password, or bearer token.

The canonical live example is model-discovered base `d847b7f4-6460-433f-b53c-4f4640c2d352`. Its tenant 1 binding uses `/demo`, the `member_id` field, a Search button, and a table balance cell. Tenant 2 uses `/demo/pine`, the `customer_ref` field, a Find account button, and a `strong` balance element. [Live evidence](../evidence/shared-capability/model-live-reuse.json) records model decisions, both successful replays, both scoped not-found results, and an isolated tenant 2 selector drift check.
